# 技术笔记写作

交付能独立阅读的文章：回答明确问题，解释必要机制，让读者知道结论或操作结果成立的条件。目录、元数据、链接和操作权限遵循根 `AGENTS.md`。

## 按请求确定范围

| 请求 | 处理方式 |
| --- | --- |
| 新写文章 | 明确读者已有知识、中心问题和关键依据，再按理解依赖组织成稿 |
| 实质改写 | 先定位理解或操作被阻断的位置，保留有效论述，修改相关段落及必要上下文 |
| 局部润色 | 直接改指定文本，保留原意和作者语气，不启动全文研究或添加固定章节 |
| 评审 | 报告有依据的问题、位置、读者影响和最小修改；文风偏好与事实错误分开 |
| 研究笔记 | 区分来源观点、自己的推断和待解问题，不把未知补成确定结论 |

用户明确要求计划、提纲或检查单时按该文体交付；内部提纲不代替用户要求的成稿。利用已有上下文作判断，只澄清会实质改变受众、主张或执行对象的信息，不要求逐节确认。

## 写作中的关键判断

- 每个必要段落推进一个问题：建立直觉、解释机制、展示证据、限定结论或引出操作。围绕难点分配篇幅，允许概念与实践交替，不套等长章节模板。
- 对决定结论的技术主张读取原始论文、官方文档或源码；版本、界面和权限等易变信息按当前条件核对。结论不超出证据范围：源码存在、产品可用、实际运行与效果评估分别判断。来源冲突时比较对象与前提，无法解决则收窄结论。引用靠近所支持的论述，教学数字不冒充实测数据。
- 教程说明会影响操作的初始状态和关键结果；涉及仓库或命令行时，再交代分支、目录、Shell 和权限。下一步需要的文件或状态必须已产生。替代路径说明分歧点及如何继续，不强制所有教程采用 Git 流程。
- 修改先处理论证与理解跳步，再删重复、改句子。保留作者真实判断和必要的不确定性，不编造经历，也不按禁词表机械替换。
- 成稿保留读者需要的解释、例子、操作、实验依据及影响结论的方法取舍；技能开发记录、作者待办和改稿往返留在工作记录。清单、图表和自测只在帮助理解时使用。

## 按难点读取方法

参考文件只在需要对应方法或例子时读取相关小节：

- 受众或选题不清：[读者与问题](references/writing-and-review.md#读者与问题)。
- 概念、公式与推导：[把推理中间层写出来](references/writing-and-review.md#概念文章)。
- 实操链路或替代路径：[让前一步的结果成为下一步的输入](references/writing-and-review.md#操作教程)。
- 资料汇总与未定结论：[资料、研究笔记与观点](references/writing-and-review.md#资料与观点)。
- 选择图表、解释图片或配套代码：[图表与附件](references/writing-and-review.md#图表与附件)。
- 结构修改或内容评审：[改稿与评审](references/writing-and-review.md#改稿与评审)。

Obsidian 特定语法按需使用 `obsidian-markdown`。交付前核对本次改动涉及的论据、推导、命令与引用，呈现检查遵循 AGENTS.md；简短说明实际验证与未验证部分，不把文件生成或会话结束等同于运行成功。
