# 技术笔记写作

让文章回答一个值得解释的问题：读者能形成正确理解，或完成有意义的操作，并知道结论成立的条件。目录、元数据、资源位置与授权遵循仓库根 `AGENTS.md`，这里提供内容判断方法。

## 按请求选择工作量

| 请求 | 产物与处理范围 |
| --- | --- |
| 新写文章 | 理解读者与中心问题，查证关键事实，交付连贯成稿 |
| 实质改写 | 找出理解或操作被阻断的位置，保留有效论述，改对应段落及必要上下文 |
| 只润色一句或一段 | 直接给修订文本；不顺带研究全库、添加固定章节或重写全文 |
| 评审 | 给有证据的问题、位置、读者影响和最小修改；把事实错误与文风建议分开 |
| 研究笔记 | 保留来源、自己的推断和待解问题；不假装结论已经确定或已经公开发布 |
| 明确要求计划或提纲 | 交付所需文体；不能把内部提纲作为用户要求的最终文章 |

不要求用户逐节确认。先利用请求、已有文章和上下文判断；只有受众、核心主张或执行对象的缺失会实质改变结果时才询问。

## 建立文章的解释线索

在工作上下文中明确：读者已知什么、想理解或完成什么、文章回答的核心问题、需要哪些依据。读者不需要看到这张工作表。

先查看本库相关笔记，防止重复造文或术语冲突。给每个必要段落一个作用：提出问题、建立直觉、解释机制、展示例子、限定结论或引出操作；按理解依赖排序，不按搜索或开发的先后排列。

概念讲解、实操教程和经验分析可以交替，但每次切换要说明联系。篇幅围绕难点分配，不把背景、步骤、总结写成等长模板。独立成篇需要新的问题或使用场景，不因章节多就拆文件。

## 研究与证据

- 涉及版本、产品界面、权限、模型能力或近期事实，查当前官方文档、论文或源码；记录适用版本或日期。
- 围绕决定文章结论的主张寻找证据与反例。搜索摘要帮助定位，打开并阅读支持主张的原文后再引用。
- 来源只能支持它实际证明的范围。源码存在、产品可用、本地跑通、云端跑通和效果评估是不同层次。
- 资料冲突时比较版本、对象和前提；无法解决的冲突收窄结论并说明不确定性。不编造 benchmark、引文、作者经历或故障故事。
- 引用靠近相关论述。常识不需要逐句引用；公开来源与仓库示例分别标明，不能把教学数字当成测量结果。

## 写成读者能用的正文

从具体问题、现象或关键结论进入。先给必要直觉，再展开机制；术语首次出现时解释其在当前问题中的作用。公式说明符号、维度和条件，并用文字解释结果；例子应支持结论，指出简化边界。

操作教程交代当前仓库、分支、目录、Shell、权限和前置文件。完整命令包含必要上下文，节选与占位符明确标注。关键操作之后解释预期现象及它能证明什么；远端写入或持续用量说明对象和停止方式。选择存在多条路径时给出明确主线，另一路注明从哪里分开、如何回到后续步骤。

图片与代码承担解释任务，不能只作装饰。正文指出图中值得观察的关系，图文中的符号与数值一致。文件资源按 AGENTS.md 放置；已有资源优先复用。

## 修改与交付

先审意义与结构，再改句子：修正无依据的结论和缺失前提，补理解桥梁，删重复，最后处理中文语序与冗词。保留作者真实判断与语气；禁词不是机械替换表，不抹去必要的技术术语或不确定性。

成稿写解释、例子、操作与结论。待办、评审往返和作者验证过程留在工作记录；与主题直接相关的实验方法和结果属于正文。清单、表格、自测按表达需要使用，不强制全部改成段落。

按改动验证：核对关键来源和推导、受影响命令及文件引用；有图表公式时检查目标界面。语法通过不能证明显示正常。远端运行须有任务授权，不能为了验证教程擅自发布、安装 App 或发送消息。

交付文章或评审结论，并简短说明实际检查与未验证部分。不把“文件已生成”称为“读者已经会用”或“部署成功”。

## 按需参考

- 新写长文、解释难点或实质改稿：读取 [写作与评审方法](references/writing-and-review.md) 中对应小节；末尾有可复用的样例验证任务。
- 调整此技能或了解方法取舍：读取 [来源与设计取舍](references/sources-and-decisions.md)。
- 需要 Obsidian 特定语法时使用项目技能 `obsidian-markdown`，不把其项目任务表示例套成博客。
