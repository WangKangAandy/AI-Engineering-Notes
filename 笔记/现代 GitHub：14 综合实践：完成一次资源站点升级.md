# 现代 GitHub：14 综合实践：完成一次资源站点升级

> 本文收录于 [AI-Engineering-Notes](https://github.com/xallor-ai/AI-Engineering-Notes)，分享 AI 技术研究、工程实践与应用探索。欢迎 Star 关注后续更新，也欢迎通过 Issue 交流和纠错。

本章不再给出完整答案，只给需求、边界和验收条件。你可以选择人工实现或使用第 12 章的 Agent 方法；两条路径都必须回到同一个 PR、CI 和交付证据。

## 新需求

让资源导航页面按分类分组，并在每组显示条目数量。保持 CSV 的三列格式、重复 URL 校验、HTML 转义和现有资源；不引入数据库、外部搜索或前端框架。

先创建 Issue，写出当前行为、预期行为和完成条件。至少包括：每条资源出现一次、分类排序规则明确、空分类和特殊字符有测试、构建页面与当前清单一致。

## 交付两档证据

基础路线需要提交：需求 Issue、实现分支、失败测试、修复后的测试、PR 评审、Check resources、构建产物、部署或本地交付结果，以及回滚/清理说明。

AI 路线额外提交：任务边界、执行环境、规则来源、Agent session、实际 diff、纠偏记录、当前 head SHA、事件自动化运行和停用状态。没有执行的云端步骤明确写未验证。

实现时先写一个能暴露旧行为的测试，观察失败，再修改最小代码。完成后从实际 PR 取得 head SHA，核对 diff 和检查结果；不要在 `main` 上寻找未合并的 Agent 修改。

如果使用第 13 章的事件自动化，代码 PR 不一定修改 `resources.csv`，因此不要强行让它触发。代码 PR 完成后，先按第 13 章恢复凭据、配置和 workflow，再创建一个有实际价值的资源更新 PR，让事件自动化产生一次可核对评论。最后停用实验自动化并清理不再需要的凭据。

## 复盘

你应该能够回答：需求在哪里定义、哪个提交实现了它、哪个测试证明了什么、CI 检查了哪个 SHA、哪个产物被交付、AI 修改和评论是否有边界、失败时如何恢复。无法回答的地方就是下一轮维护 Issue，而不是在结论中写“已完成”。
