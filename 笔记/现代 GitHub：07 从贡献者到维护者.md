# 现代 GitHub：07 从贡献者到维护者

> 本文收录于 [AI-Engineering-Notes](https://github.com/xallor-ai/AI-Engineering-Notes)，分享 AI 技术研究、工程实践与应用探索。欢迎 Star 关注后续更新，也欢迎通过 Issue 交流和纠错。

本章回答一个比“怎样提交 PR”更长期的问题：一个项目怎样让陌生贡献者知道如何参与，维护者怎样分配责任，又怎样避免模板和权限变成形式主义。前置是你已经完成一次 PR，并理解 Issue、分支和评审。

## 先写清贡献入口

在 resource-nav 的 main 中维护三份入口：README 说明项目面向谁，CONTRIBUTING.md 说明怎样贡献，Issue/PR 模板让新任务提供足够信息。它们是不同文档，不要把所有规则复制三遍。

README 只说明项目用途、资源格式和链接；贡献指南说明收录标准、提交前检查和 PR 描述；Issue 表单收集资源标题、URL、分类和来源理由；PR 模板提醒作者列出差异、测试和未验证内容。

这些文件应通过一个正常 PR 进入 main。不要在本文中要求读者直接修改默认分支，也不要把“模板文件存在”写成“GitHub 页面已经加载模板”；合并后再打开 New issue/New pull request 入口验证。

## 谁可以做什么

个人仓库的 owner 可以调整设置和合并；collaborator 的权限取决于授予的角色。公开可读不等于任何人可以推送或修改规则。组织仓库还有更细的 triage、write、maintain、admin 角色，不能把组织权限界面机械套到个人仓库。

只授予完成任务所需的权限。评审责任和机器门禁是两回事：本章说明谁负责阅读和决定，本书第 09 章才把真实检查配置成合并条件。CODEOWNERS 可以表达路径责任，但它不自动保证每条需求都被正确验收，也不替代分支保护。

## 外部贡献的完整边界

对别人的公开仓库，通常只能读取，不能向其分支推送。fork 是你管理的远端副本；在 fork 中创建分支、提交并推送，再向上游仓库创建 PR。创建 fork 不会继承上游的 Secrets、Pages、Rulesets 或 App 安装。

外部贡献前先读目标仓库的 README、CONTRIBUTING、许可证和相关 Issue。确认它接受这类修改后，才选择真实需求。外部克隆应放在独立目录，不要与自己的 resource-nav 混用；进入新目录后核对 `git rev-parse --show-toplevel`、origin 和本地署名，再开始修改。

一次外部贡献的验收仍然是 PR 的差异、检查和维护者决定。你可以在自己的 fork 验证，但不能把 fork 中的绿色结果写成上游仓库已经验证。

## 验收维护制度本身

在自己的 resource-nav 合并入口文件后，检查 README 的贡献链接、Issue 表单字段和 PR 模板的预填内容。若页面没有显示，先检查文件路径、默认分支和模板格式；不要把静态文件存在当作平台加载成功。

本章结束时，你拥有最小的贡献入口、清楚的权限责任和一条外部贡献路径。下一章把已有程序接回这套协作制度，并让错误真的阻止合并。
