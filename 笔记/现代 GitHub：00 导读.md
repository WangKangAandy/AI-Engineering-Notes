# 现代 GitHub：从入门到实战与 AI 自动化

> 本文收录于 [AI-Engineering-Notes](https://github.com/xallor-ai/AI-Engineering-Notes)，分享 AI 技术研究、工程实践与应用探索。欢迎 Star 关注后续更新，也欢迎通过 Issue 交流和纠错。

这本书面向有基本电脑操作能力、但还不会系统使用 Git 和 GitHub 的读者。你不必先会编程：前半部从网页上的仓库与一次小修改开始，后半部再引入一个可以看懂、运行和验证的小型 Python 项目，最终让 AI 在明确边界内参与工作。

贯穿项目是“学习资源导航”。我们先维护资源的标题、链接和分类；随着协作需要增加，用程序校验清单并生成静态页面，再接入测试、CI、部署与 AI 辅助。每一项工具都为这个项目解决一个具体问题。

## 学完以后应当能做什么

完成通用实战后，你应能接到一个新需求，写清问题，在本地创建修改，通过 PR 讨论和修订，使用 CI 与规则保护合并，并把结果发布出去。遇到冲突、错误提交或失败运行时，能找出当前状态，再选择恢复方式。

AI 部分继续使用这些能力：你要判断任务是否适合委派，提供项目上下文，限制允许的操作，检查实际差异和测试。随后把一个手动验证过的任务变成真实事件触发的自动化，观察输出、重复与失败，最后停用和清理。只有 Agent 显示完成，不能作为全书的毕业结果。

这不是 Git 或 Python 的所有功能手册，也不要求同时开通每种 AI 产品。能说明何时需要一项能力、如何验证结果，比把所有开关打开更重要。

## 先准备一个自己可以管理的仓库

主线在第 2 章创建个人公开仓库 `YOUR_LOGIN/resource-nav`，默认分支统一为 `main`。YOUR_LOGIN 是你的实际 GitHub 用户名，所有 Issue、PR、Actions、Pages 与 AI 任务都核对这个目标。公开仓库只放可以公开的练习内容。

本书源仓库是阅读资料，不是读者的实验仓库。只有真实、准备贡献的修改才发给真实项目；实验 PR 不发送到本书组织。Self-hosted Runner 专题单独使用私有 `runner-lab`，因为在个人机器上执行代码需要不同的信任边界。

主线本地命令以 Windows、PowerShell 7 为例。第 3 章准备 Git 和 gh，第 12 章再准备 Python 3.12。不要在不知道当前目录时照抄命令，也不要把 PowerShell 写法机械移进 Linux shell。Actions 初始使用托管 Ubuntu，环境差异将在第一次运行时说明。

Git 提交署名、GitHub 网页账号、Git 传输认证、gh 登录和模型认证是不同对象。每章在真正使用它们时解释配置，不假设前一个工具登录成功后所有工具就共享了身份。

## 同一个项目怎样逐步成长

| 阶段 | 已有内容 | 新增能力 |
| --- | --- | --- |
| 第 2 章结束 | README.md、resources.csv，两条初始资源 | 用网页提出需求、分支修改并合并 |
| 第 3～6 章 | 同一仓库的本地副本 | 提交、同步、冲突与恢复；隔离练习不替换主仓库 |
| 第 7～11 章 | 资源与说明的真实变更 | 子任务、评审、贡献约定和进度组织 |
| 第 12 章 | catalog.py、test_catalog.py、build.py、.gitignore | 校验数据、测试程序、生成 site/index.html |
| 第 13～18 章 | workflow、规则、运行与部署记录 | 自动验证、产物传递、发布、回滚与维护 |
| 第 19～23 章 | 已有可测试、可审查的项目 | Agent 任务、持久上下文和事件自动化 |

完成一个 PR 后回到 main 拉取最新内容，再开始下一项任务；未完成的修改先处理，不靠强制覆盖恢复“教程状态”。清单可以增加资源，章节不会假设每个人始终只有相同条数。程序测试的数量和校验出的资源条数也是不同结果。

读到中途重新开始时，先检查仓库文件、当前分支、未提交修改和最近一次合并。第 12 章提供完整程序附件，但它们不能代替你核对仓库级的规则、Secrets、环境和安装授权；Git 文件恢复不会自动恢复这些设置。

自建 GitHub App 不必先于使用现成 Agent。包与容器发布、复杂集群、企业 SSO、多 Agent 编排可以在产生实际需求后进一步学习；本书不借这些选项要求初学者搭建一套庞大基础设施。

## AI 主线的两种执行位置

第 19～21 章选择 GitHub Copilot 的云端 Agent，明确其任务环境与仓库；第 22～23 章转到 GitHub Actions 中的 gh-aw，并选择 Copilot 引擎。复用的是项目、任务约定和验收方法，不是同一个会话，也不是自动继承模型凭据。

第 22 章会重新解释事件从哪里来、谁调用模型、在哪里执行、允许写什么以及哪里查看结果。个人仓库采用适用的个人认证路线，组织集中计费作为替代。实际功能资格、组织策略和用量应在启用前核对；没有资格时可以完成前四部分，但不能把未执行的 AI 实验标为通过。

CI 处理确定性的数据规则；AI 辅助解释资源变化、形成摘要或提出需人工判断的意见。AI 评论不等于批准，模型输出不可以自行扩大工具权限，事件成功也不保证结论可靠。

## 如何判断自己真正完成了练习

每章都将结果对应到可观察对象：文件内容、提交、Issue/PR 状态、测试输出、运行日志、artifact、部署页面或 Agent 产生的修改。记录当前运行与提交，不能把旧的绿色状态当作新改动已验证。

本机测试只证明本机执行结果；YAML 能解析不证明云端权限已配置；本地 Webhook 样例通过不证明公网事件已经投递。书中给出应观察的结果，读者需要在自己的环境中核对；没有执行的步骤应明确保留为未验证。

需要结束实验时，区分停止当前运行、禁用未来触发、撤销凭据、移除安装和下线站点。关闭 Issue、删除分支或删除 Release，不会自动停止所有工作。相应章节在完成实践后说明退出路径。

从[看懂 GitHub 上的一个项目](<现代 GitHub：01 看懂 GitHub 上的一个项目.md>)开始，先获得一次简单而可验证的成功，再逐步增加复杂度。
