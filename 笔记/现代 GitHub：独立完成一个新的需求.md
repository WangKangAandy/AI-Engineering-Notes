# 现代 GitHub：独立完成一个新的需求

> 本文收录于 [AI-Engineering-Notes](https://github.com/xallor-ai/AI-Engineering-Notes)，分享 AI 技术研究、工程实践与应用探索。欢迎 Star 关注后续更新，也欢迎通过 Issue 交流和纠错。

本书第 24 章。[全书导读](<GitHub 协作与自动化：01 学习路线.md>) · [上一章](<现代 GitHub：让 AI 自动化可观察、可停止、可持续.md>)

前面的章节给出了操作路径。本章换一项没有逐步实现答案的需求，检验你能否选择合适的方法、完成变更，并用证据说明结果。仍使用自己的 resource-nav，不需要创建另一套产品、开通所有专题服务或运行多个 AI 平台。

## 先确认起点是真实状态

从 main 的最新版本开始，检查工作区、资源清单、程序与 CI。至少应能运行清单校验、单元测试和构建，能找到 Check resources 的最近结果。如果已完成 Pages，能从上线页面追到部署 run 与 SHA；尚未完成发布资格的读者，只能记录构建交付结果，不能写成网站已上线。

AI 部分需要第 19～23 章的环境与事件自动化。尚未具备产品资格时，可以先完成通用实战，再补 AI 证据；不要用阅读日志截图代替自己完成了一次任务。

## 新需求：让分类在页面中真正帮助阅读

目前页面逐条显示资源，并在标题后注明分类。资源增加后，读者希望相同分类的条目集中展示，更容易浏览。

请先创建 Issue，用自己的话说明当前行为、预期和不包含的范围。一个可用的验收约定是：

- 页面按分类分组，每个实际出现的分类有一个可见标题。
- 分类的排列有明确规则，例如按分类名排序；组内保留清单顺序。只选一种并写清，不让实现者自行猜测。
- 每条有效资源恰好出现一次，标题与链接正确，特殊字符仍按文本展示。
- 现有 CSV 校验规则不变，不因为改页面而放宽重复 URL 或空字段检查。
- 不引入数据库、外部检索、登录功能或前端框架。

若此前已经实现完全相同的功能，先说明现状，再选择同等规模的新需求，例如为每个分类显示条目数；不要为完成练习重复提交没有价值的改动。

## 先设计证据，再选择人工或 AI 实现

在修改前列出至少一个“旧代码不满足、新代码满足”的测试。测试应检查行为，例如两类资源分别归组、条目不遗漏或重复、分类文字不会作为 HTML 执行；不要只断言实现中某个私有变量恰好叫某个名字。

决定怎样实施：自己编写，或让 Agent 完成有边界的修改。两条路径最终经过同样的 PR、CI 和验收。给 Agent 的任务应引用 Issue，指定 main 基线、允许修改的文件、保持不变的输入格式、测试与构建命令，并要求报告没有执行的检查。

这次主要变化在页面构建与对应测试。Agent 如果提出改 workflow 权限、添加不需要的依赖或重写整个目录结构，你需要判断这些是否支持当前需求，而不是因为“看起来更完整”就接受。

## 从分支到 PR，保留问题和修订记录

在新的工作分支完成实现。先观察新增测试如何暴露旧行为，再修改程序并运行完整检查。核对资源清单没有被意外改写，构建页面与 Issue 约定一致。

创建 PR 时说明问题、最终行为、验证与限制，关联实际 Issue 编号。检查最终差异，不只检查最后一次修复提交。得到反馈后在同一来源分支修订，再请复查。

单人练习可以记录作者自查，但不能写成独立评审通过。使用 AI 审查也应标明执行者和检查范围，不能冒充另一位有责任的维护者批准。仓库要求的人工审批仍需符合规则的人完成。

合并方式按第 8 章的取舍选择。若使用 Squash and merge，记录实际进入 main 的新提交；后续部署与回滚应针对这个结果，而不是把来源分支中的旧 SHA 当成主线版本。

## 验证交付的是这次修改

确认当前 PR 的 CI 检查了正确提交并实际执行了测试。不要通过删测试、允许失败或绕过规则让红灯消失。条件满足后合并，再观察 main 的运行与产物。

如果保留了 Pages 审批，核对待发布的 SHA、测试和产物后批准。打开实际站点，对照分类分组、排序与条目数量；浏览器页面、部署记录和 PR 应能互相对应。发布 Release 时同样选定验证过的提交，不能只看到 main 名字就默认它还停在刚才的版本。

遇到问题时先定位阶段：输入数据、实现逻辑、测试、workflow、权限还是部署传播。依据前面章节选择修复或回滚，并为新的结果留下新的提交与运行记录。

## AI 自动化还要单独核对

沿用第 22 章的一种事件自动化，不新增第二套。本次需求主要改页面生成逻辑，未必会修改 `resources.csv`，而第 22 章的事件故意只监听资源清单变化；不要为了让路径匹配而把不相关数据塞进代码 PR。完成代码 PR 后，按第 23 章的恢复流程核对凭据、配置和 workflow 是否已启用；确认启用后，再从最新 main 建立一个很小的后续 PR，只向 `resources.csv` 添加一条真实、不重复的资源，用它触发既定的辅助任务，查看它收到的上下文、输出位置与实际内容。若该事件只在 PR 打开时发生，后续推送修订不自动产生新输出是预期行为，不要把旧摘要当成对最新提交的审查。

抽查摘要中的事实能否从 PR 差异或文件找到依据。评论若遗漏关键限制，要记录并修正提示或工具输入；事件运行绿色不代表摘要内容正确。按第 23 章的方法观察一次重复或失败处理，先检查是否已经有写入，再决定是否重跑。

完成后停止本次实验需要停止的运行，禁用不再需要的未来触发；凭据或安装只有确认没有其他用途时才撤销。站点、workflow、App 安装和模型调用各有生命周期，不会因为 Issue 已关闭就同时消失。

## 用一份简短记录交付结果

可以在完成的 Issue 或 PR 中整理以下证据；实际链接由你填写，没有完成的项目明确标为未验证，不复制空白清单充当结果：

| 证据 | 它能说明什么 |
| --- | --- |
| Issue 与完成条件 | 为什么需要这次变化，什么才算完成 |
| 最终 PR 与合并提交 | 实际改动范围、讨论和进入主线的版本 |
| 测试案例与执行结果 | 新行为和原有约束经过了哪些检查 |
| CI run 与产物 | 哪次执行验证并构建了哪个提交 |
| 部署与页面检查 | 访问者得到的是否为已验收版本 |
| Agent 会话与纠偏记录 | 委派了什么，实际修改了什么，你如何判断结果 |
| 事件运行、输出与停用记录 | 自动化是否按约定触发、写入并结束 |

若某一阶段失败，能说明原因并恢复到明确状态，也是重要能力；不能把失败写成通过。真正完成这本书的实践，是能够对一项新需求解释每个决定，并把最终结论落到文件、提交、测试、运行和交付记录上。
